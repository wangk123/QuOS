# QuOS · 需求文档

> 2026-09-23 立项讨论整理。✅=已讨论清楚（详述）；🔲=方向已定、细节未展开（大纲，待后续模块 spec 时讨论）。

## 1. 背景与定位 ✅

### 1.1 平台定位

质量操作系统：全质量域模块化集成（需求整理、案例设计、缺陷管理、回归自动化、性能、安全），为 AI 深度协作的测试流程设计。当前单人使用，架构不设单人限制。

### 1.2 设计背景（平台须在此场景下立即有用）

- 需求输入碎片化：多数需求无文档；有也是碎片、过期文档、开发过程文档或 AI 生成文档；需求与开发以口头交流为主，开发凭理解 + AI 补充直接开工
- 测试资源紧张，开发全员 AI 辅助节奏快，传统测试流程跟不上
- 测试对流程无强制约束力：需要工具承载流程与闸门，而非依赖团队自觉
- AI 使用无环境限制（可自由使用外部大模型）

### 1.3 设计哲学（五条，全平台通用）✅

| # | 哲学 | 内容 |
|---|---|---|
| 1 | 资产统一 | 一棵功能树贯穿全程：需求卡片挂叶子 → 案例组挂卡片 → 缺陷聚集挂模块 → 回归范围 = 受影响子树 |
| 2 | 文件为源 | Markdown + git 是唯一真相源，平台只是编排器和视图层；数据永不锁死，基线 = git commit |
| 3 | AI 编排化 | 每个动作一个 AI 任务，prompt 模板即流程知识，版本化积累 |
| 4 | 闸门内建 | 人工闸门（核验/判读/终审）是平台功能不是自觉——AI 幻觉/漏扫靠闸门兜住 |
| 5 | 判断复利 | AI 出初稿、人做砍/补/锚，过程中把判断沉淀成 if-then 规则库反哺 AI |

### 1.4 人机分工总则 ✅

AI 供给：规模（生成量）、一致性（不倦）、速度。人供给：私有历史（生产坑）、领域不变量、组织现实、责任签名。界面固定为流水线：**AI 初稿 → 人砍/补/锚 → 判断沉淀 if-then → 规则库反哺 AI**。

## 2. 内核需求

### 2.1 功能树 ✅

- 任意层级（不限 3 层），节点增删改（加子节点/改名/删除；删除时断言保留在证据层可重挂）
- 树为唯一导航：需求/案例/缺陷/回归都挂节点；任何变更必须能唯一定位到节点，定位不了 = 缺节点
- 节点状态徽章：待确认数（琥珀）、断言数（灰）、已实证（绿对勾）
- 交互规范：IDE 文件树风格——缩进引导线、SVG 箭头旋转展开、选中左指示条、hover 出图标操作（加/改/删）
- 主轴选择：业务流程为主轴，代码结构做校验
- 🔲 折叠状态持久化、节点拖拽移动、跨项目树复制

### 2.2 证据池 ✅

- 项目级材料库，不属于任何节点；整理节点时从中勾选关联
- 输入统一为一个智能输入区，自动识别：

| 输入 | 识别为 |
|---|---|
| `git@` 开头 / `.git` 结尾 / github·gitlab·gitee 链接 | 仓库（尾部 `feature/xx` 或 `@feature/xx` 解析为分支） |
| ⌘V 粘贴图片 | 截图材料 |
| 其他文本 | 文本材料（URL 标注"文本·链接"） |
| 拖入文件 | 按扩展名归文档/压缩包（txt/docx/xlsx/md/pdf/zip…） |

- 可信度分治：代码 > 实际系统 > 口头/聊天 > 开发文档 > 旧文档 > **AI 生成文档（最危险：格式漂亮 ≠ 真实，断言强制「待实证」逐条核实后才升级）**
- 🔲 仓库定时同步、文档版本比对（同文档多版本）

### 2.3 基线管理 ✅

- git commit + tag 版本化；版本时间线；两版本 diff
- 增量定位：新变更 diff → AI 映射功能树 → 受影响卡片清单 → 只重跑该子树；定位结果必须人工过目再触发（定位漏 = 增量失真）
- 🔲 跨项目基线对比

### 2.4 AI 编排器 ✅

- 任务注册表：每动作一个任务类型（extract / conflict / gap / assemble / impact / 后续 casegen…）
- prompt 模板库版本化（prompts/ 目录，git 管理）
- 每个任务定义验收闸门（如 extract 的全量核验）
- 🔲 多模型路由（不同任务用不同模型）、成本统计

### 2.5 判断规则库 🔲

- 机制已定（判断显性化三层法：做了什么判断 → 依据什么模式 → 写成 if-then），是资深测试经验的资产化载体
- 待展开：规则的存储格式、在流程中的注入点、与 prompt 模板的合并方式

## 3. 模块需求

### 3.1 M1 · reqspec 需求整理 ✅（详见 `docs/specs/2026-09-23-reqspec-design.md`）

两级流程：项目层（证据池/功能树/基线）+ 节点整理层六步（提事实→挑矛盾→找空白→成卡片→问人→存档）。

### 3.2 M2 · casegen 案例设计 ✅（设计共识已定，待写 spec）

挂接 reqspec 卡片树（同一棵树）：

- **C↔R 双向追溯**：每条规则 R# 至少映射 1 条案例；砍案例自动暴露无覆盖规则 → 未覆盖清单自动生成
- **分层生成**：高风险 = AI 完整用例 + 人审留档（免责证据）；中低 = AI checklist（分钟级）；紧急 = 纯探索 + 事后补记
- **AI 生成限定规则**：每叶子案例数上限（≤12，超了拆节点）；类型配额 主路径:异常:边界 ≈ 2:4:4（纠正 AI 无风险观）；预期不可判定的禁止生成 → 进待澄清
- **分块评审**：一块 = 一个功能点案例组（5-15 条），时间盒 5-10 分钟，整块决策：通过/修改/降级/舍弃（记原因）；未审完的块自动按 AI 建议优先级走（决策显式）
- **优先级体系**：P0 不变量+高风险边界 / P1 异常+状态转换 / P2 主路径 / P3 边缘；节点级优先级，案例继承——整块舍弃/降级在节点操作
- **案例条目格式**：`ID | 优先级 | 类型标签 | 一句话（含关键数据）`；类型标签引导审核注意力
- 🔲 spec 细化：评审界面形态、案例执行状态流转、与 M4 回归的衔接字段

### 3.3 M3 · defect 缺陷管理 🔲（大纲）

- 缺陷记录挂树节点；缺陷聚集分析（80/20 模块分布）反哺风险分级先验
- 每缺陷问「本可如何发现」→ AI 流水线生成预防规则 → 入判断规则库
- 缺陷趋势（新发现率收敛）作为准出量化依据
- 待讨论：缺陷字段最小集、与 IM 的录入通道、生产问题回流路径

### 3.4 M4 · rerun 回归自动化 🔲（大纲，核心机制已定）

- **事件驱动替代版本驱动**：开发提交变更 → AI diff 定位受影响子树（复用 impact 任务）→ 激活对应案例组 + 关联节点回归——用例跟节点走，不跟版本走，1 人产能模型从「串行跟版本」变「并行订阅开发事件流」
- 接口自动化资产库：AI 生成脚本 + 人审，个人可带走（不依赖公司 CI）
- 待讨论：订阅触发方式（commit webhook / 手动粘贴）、脚本运行器、UI 层自动化是否纳入（当前结论：不投入，脆性高）

### 3.5 M5 · perf 性能 🔲（大纲）

接手既有性能测试平台经验：压测任务编排、报告 AI 归因、监控采集；作为模块接入共享树与基线。待讨论：与既有 JMeter 资产的迁移。

### 3.6 M6 · sec 安全 🔲（大纲）

安全扫描编排、漏洞挂树、修复回归。待讨论：扫描器选型。

## 4. 非功能需求 ✅

| 项 | 要求 |
|---|---|
| 技术栈 | Vue3 + Vite / Python FastAPI / 文件系统 + git（无数据库，SQLite 仅索引缓存）/ LLM API 直连 |
| 部署 | 本地单机起步，零运维；架构允许后续服务化 |
| 交互底线 | 完整交互不许静态假图；人话命名；UI 遵循 IDE 级规范（图标/徽章/引导线） |
| 数据可迁移性 | 平台挂了数据还在（文件为源）；导出 md 不锁死 |
