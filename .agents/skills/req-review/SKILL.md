# 需求评审门（req-review）

req-organize 产出的草案在交付（进入人工评审或落库到需求管理平台）**之前**必须过本门。检查三件事：**内容完整吗、可读吗、规范吗**。不检查业务规则是否合理——业务歧义走消歧循环出题，不是 review 的活。

## 评审者纪律

1. **独立读者原则**：独立于**生成过程**——审草案时只用草案本身（可参照原始素材），不引用生成者的记忆与解释。评审历史（上轮报告留档）不在此列，两轮比对以上轮报告文件为准；
2. **逐条判据给证据**：每个结论必须指到位置（章节 / 规则号 / 原文引句）。禁止「整体还行」「基本清晰」这类无锚点判词；
3. **review 不改业务**：发现业务歧义 → 转入 req-organize 问题清单出题送人，review 只管文档形态。

**显式空位的统一处理（跨组规则）**：草案中显式标注【TBD/待确认】且已登记进问题清单（核验以文档内附录的问题清单为准）的缺口，在任何判据组均记「⏸ 挂起-待用户裁决」，不算打回、不算通过；未显式声明的暗漏照常打回。报告记法统一用「⏸」；单判据多子项时：有 ❌ 整条记 ❌，无 ❌ 有 ⏸ 整条记 ⏸ 并注明细。重叠判据（如成功标准同时落在 A1 与 C2）只在 C 组计分，A1 引用其结论。

## 判据

### A 规范组（逐条机械过）

| # | 判据 | 不过的样子 |
|---|---|---|
| A1 | 文档头完整：日期、范围、读者对象；背景与目标有成功标准 | 读者对象缺失、成功标准空话 |
| A2 | 术语表与正文一致：词条在正文实际使用；无同概念多写法 | 「用户/会员」混用、死词条 |
| A3 | 规则带稳定编号；每条规则能反推出至少一种可观察的违反情形（显式写出「怎样算违反」更佳；与条文原句复述雷同 = 不过） | 无法判定、violation 复读正文 |
| A4 | 结构化内容成块：参数/清单在 table（md 表格），主链路在 figure（mermaid 或箭头链路），状态枚举在 states（状态链/状态表）；不拆散塞进规则 text | 表格内容散落在规则句里 |
| A5 | 图文表文同责：图/状态链与文字规则行为一致；同一批参数在表与规则 text 两处出现时必须一致（一处维护一处引用才是常态） | 图说 A→B、文说 B→A；表改了 text 没改 |

### B 可读性组（读者测试，B1 是核心）

**B1 独立读者六问**：以独立读者身份只读草案回答，答案写入报告——
1. 这系统解决什么问题、怎么算成功？（背景与目标可达，只答出「系统是什么」不算过；显式 TBD 记 ⏸）
2. 谁在用它？每人怎么用？（用户类与场景可达）
3. 任选三章：这章管什么、为什么存在？（背景是动机，不是出处引用句）
4. 主链路：核心流程从入口到出口经过哪些环节？（figure 或叙述可达）
5. 任选五条规则：怎样算违反？（可判定，可由行为断言反推）
6. 任选一个用户类：照着场景叙述走一遍，故事讲得通吗？（缺触发/缺结果/缺异常即病）

有 ❌（非 ⏸）= 该处文档病，记入打回清单并指到位置。B1 出 ❌ 时 B2/B3 照常执行（判据一次出齐，避免多轮往返）。

**B2 堆砌与结构检测**（计数单位 = **最小编号容器**：有小节按小节算，无小节按章算；一切带编号的行为断言均计入，GP/NFR 同计）：
- 单容器规则数 > 12 → 疑似拆解倒灌，该合并的合并、该进 table 块的进块；
- 单容器规则均值 < 25 字（按字符计，不含编号前缀与标点；URL/参数名等代码片段照计）且通篇条件断言、无叙述衔接 → 疑似测试点列表冒充需求；
- 背景是模板句（「源自总览 X.X」式索引/套话）→ 打回写动机；
- **章节目录=系统内部模块的镜像**（目录长得像代码包结构/架构分层图，任何一章都挂不到用户类或场景）→ 结构性堆砌，打回重排章节；
- 功能孤儿章：抽 2 章问「服务哪个用户类的哪个场景」，答不出的章要么补挂靠、要么降级移除。

**B3 原始需求可还原（两个操作都要做）**：
1. 读者复述：读完用三句话复述「原始需求是什么、这版覆盖什么」——复述不出来 = 文档丢了原始需求的样子，打回；
2. 忠实性核对：对照原始素材逐域扫一遍——素材明示的功能点、页面/路由、参数、约束、现状口径，**漏收且未显式声明不收 = 打回**。粒度：功能行为必须收；UI 级命名（页签/按钮/组件名）不强制逐项收，但其承载的功能行为缺失仍算漏收。

### C 完整性组（对照骨架，暗漏即打回；显式空位记 ⏸）

| # | 判据 | 缺的样子 |
|---|---|---|
| C1 | 用户与场景：有用户类清单；直接操作系统的每个用户类至少一条端到端场景叙事 | 只有「系统」没有「人」 |
| C2 | 背景与目标：业务痛点 + 成功标准 + 明确不做什么 | 只有功能没有「为什么做」 |
| C3 | 系统总览：主链路图 + 上下文图（外部人/系统/依赖与数据流向） | 读者不知道边界在哪 |
| C4 | 约束、假设与开放问题：外部依赖清单（挂了会怎样）、TBD 显式列出 | 依赖隐藏在规则里、悬而未决的问题不可见 |
| C5 | 数据实体：核心业务实体及关系可从文档述出 | 读者拼不出「一张受理单里有什么、和文档什么关系」 |
| C6 | 非功能覆盖：性能/安全/可靠性/可维护/合规逐项过，缺的补条目或显式声明「不适用」（近义覆盖可接受，如以「可用性」声明覆盖「可靠性」，但需点名对应） | 非功能只剩零散三条 |

**按需取用型文档**（如从存量系统反写的测试基线，由文档头自述或素材定位声明）：C 组判据降为「缺口显式声明」，A/B 组照常。

## 流程（不限轮次，直到通过）

1. 按 A → B → C 顺序逐条检查，产出报告：

```
## req-review 报告（第 N 轮）
判据: A1 ✅/❌/⏸ A2 … B3 … C1 …（六问答案附后）
打回清单:
| # | 位置 | 问题 | 判据 |
|---|---|---|---|
结论: 打回（N 项）/ 通过 / 挂起项 N 条待用户裁决
```

2. 结论**打回** → 回 req-organize 修改（只改打回清单指到的地方，不重构无关内容；对改动条款重跑五查相关项）→ 重新**全量** review（不是只查上轮打回项——修改可能引入新问题）；
3. 结论**通过**（⏸ 挂起项单独列给用户）→ 草案才可交付；报告留档随草案走；
4. 连续两轮打回项完全相同 = 修改无效，停下来向用户说明卡点，不无限自循环。

## 与校验工具的分工（若接入）

结构合法性校验（quote 出处定位、编号闭合、块结构完整）可交给校验工具/平台代跑，review 不重复；**未接入工具时这些结构检查由 review 顺带执行**。工具判不了的——violation 是不是真判定、术语是否混用、读者能不能看懂、结构是否堆砌、内容是否缺层——永远是本门的活。
