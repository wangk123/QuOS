# 需求评审门（req-review）

req-organize 产出的草案在交付（进入人工评审或落库到需求管理平台）**之前**必须过本门。只检查两件事：**文档是否规范、是否可读**。不检查业务规则是否合理——业务歧义走消歧循环出题，不是 review 的活。

## 评审者纪律

1. **独立读者原则**：审草案时只用草案本身，不引用生成过程的记忆。判断标准是「一个没参与生成的人只靠这份文档能不能看懂」——生成者自己审自己是所有漏检的来源；
2. **逐条判据给证据**：每个结论必须指到位置（章节 id / 规则号 / 原文引句）。禁止「整体还行」「基本清晰」这类无锚点判词；
3. **review 不改业务**：发现业务歧义（两个规则该信哪个、边界没定义）→ 转入 req-organize 问题清单出题送人，review 只管文档形态。

## 判据

### A 规范组（逐条机械过）

| # | 判据 | 不过的样子 |
|---|---|---|
| A1 | 文档头完整：meta 有日期与范围；overview 有 intent（为什么做）与 boundary（不做什么） | 范围空话、boundary 缺失 |
| A2 | 术语表与正文一致：每个词条在正文实际使用；正文没有同概念多写法（查名实） | 「用户/会员」混用、死词条 |
| A3 | 规则带稳定编号、violation 是真判定（不复读 text 原句） | violation 与 text 雷同 |
| A4 | 结构化内容成块：参数/字段/契约清单在 table 块，主链路在 figure 块，状态跳转在 states 块 | 表格内容拆散塞进规则 text |
| A5 | 图文同责：states/figure 块与文字规则描述的行为一致 | 图说 A→B、文说 B→A |

### B 可读性组（读者测试，B1 是核心）

**B1 独立读者四问**：以独立读者身份只读草案，回答——
1. 这个系统是干什么的、给谁用？（overview 可达）
2. 任选三章：这章管什么、为什么存在？（background 是动机叙述，不是出处引用句）
3. 主链路：核心流程从入口到出口经过哪些环节？（figure 或叙述可达）
4. 任选五条规则：怎样算违反？（violation 可判定）

答不上来或含糊 = 该处文档病，记入打回清单并指到位置。四问全过才进 B2。

**B2 规则堆砌检测**（「看着跟测试功能点似的」的特征）：
- 单章规则数 > 12 → 疑似拆解倒灌，检查是否该合并为行为级规则或移入 table 块；
- 规则 text 均值 < 25 字且通篇条件断言、无叙述衔接 → 疑似测试点列表冒充需求；
- 背景是模板句（「源自总览 X.X」「适用于所有功能域」式索引/套话）→ 打回写动机。

**B3 原始需求可还原**：读者读完用三句话复述「原始需求是什么、这版覆盖什么」——复述不出来 = 文档丢了原始需求的样子，打回。

## 流程（不限轮次，直到通过）

1. 按 A1-A5、B1-B3 顺序逐条检查，产出报告：

```
## req-review 报告（第 N 轮）
判据: A1 ✅ A2 ❌ … B3 ✅
打回清单:
| # | 位置 | 问题 | 判据 |
|---|---|---|---|
| 1 | ch-api / API-18 | 接口契约原文塞规则 text，应成 table 块 | A4 |
结论: 打回（3 项）/ 通过
```

2. 结论**打回** → 回 req-organize 修改（只改打回清单指到的地方，不重构无关内容）→ 重新全量 review（不是只查上轮打回项——修改可能引入新问题）；
3. 结论**通过** → 草案才可交付（进入人工评审或提交落库）；报告留档随草案走（自查留痕的一部分）；
4. 连续两轮打回项完全相同 = 修改无效，停下来向用户说明卡点，不无限自循环。

## 与校验工具的分工（若接入）

结构合法性校验（quote 出处定位、编号闭合、块结构完整）可交给校验工具/平台代跑，review 不重复；工具判不了的——violation 是不是真判定、术语是否混用、读者能不能看懂、规则是否倒灌——是本门的活。工具校验是底线，本门是「可以进入人工评审」的标准。本 skill 独立通用，无工具时五查全由 req-organize 自查 + 本门人工判。
