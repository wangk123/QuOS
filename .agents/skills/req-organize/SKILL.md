# 需求整理（req-organize）

把分散的意图收敛成一份可判定的共识文档，并维持其在时间轴上的有效性。

**文档首先是给人读的，其次才是给机器拆的。** 交付物是一篇读者读完能明白「系统是什么、为什么这样、怎么运转」的文档；规则编号是骨架，不是文档的全部。读者只看到规则堆砌、看不出原始需求长什么样的交付物不合格。

## 角色分工

**AI 加工，人裁决。** 提取、聚合、自查、差异分析是 AI 的活；意图供给、共识确认、冲突终裁只能是人的活。AI 只能问，不能替用户想。

## 流程

1. **素材采集**：接受口述（快但失真）、碎片文档（断章）、代码（精确但会把实现偏差固化成需求——从代码反推必须标注送人确认）、记忆（重述走样）四类素材；
2. **提取聚合**：产出草案 + 问题清单。草案中 AI 推测补充的内容显式标注，不冒充确定内容。问题清单只出三种题：选择题（给方案与后果）、确认题（写自己的理解让用户纠正）、填空题（问未定义的行为），不出阅读理解题；
3. **消歧循环**：提问 → 回答 → 再收敛，循环至问题清单清空。问不到的歧义会固化成条款里的暗坑；
4. **review 门（强制）**：草案必须经 req-review 检查，不通过的按打回清单修改后重审，循环至全过。详见 req-review skill；
5. **定稿与版本化**：用户逐项确认后定稿打版本号。

迭代（新素材 + 旧基线）同管线，多一步差异分析：新素材与基线的每个冲突强制用户二选一——意图演进（改文档）或实现偏差（改代码），不允许「先不管」。

## 写作纪律（什么是合格的文档内容）

- **背景写动机**：每个功能为什么存在，一两句事实性叙述。禁止写成出处引用句（「源自总览 2.3」不是背景，是索引）；
- **规则收敛到行为级**：一条规则说一个行为约束。测试点级断言、参数明细、字段列表、接口契约原文**不进规则 text**——它们是拆解产物或附属资料，倒灌进规则就是拿测试设计冒充需求；
- **结构化内容用块，不拆散**：参数表/字段清单/接口契约 → `table` 块；主链路流程 → `figure` 块（每行一条「节点 → 节点」链路）；状态跳转 → `states` 块；失败/超时/依赖挂掉的处理 → `exceptions` 块；衔接性叙述 → `para` 块。凡是被拆散塞进规则文本的表格内容都算违规；
- **主链路必须落图**：每个核心流程至少一条 figure 链路，让读者三十秒看懂主干；
- **章节按功能自然边界组织**：内容多的域用子章（`parent`）分层，不是每章都要凑齐所有块——缺状态机的章不写 states，没有异常路径的章不写 exceptions，内容决定结构；
- **术语表与正文一致**：词条是正文实际在用的词；同一概念全文只用一个名字。

**三不要**：不要愿景渲染和形容词堆砌（叙述≠营销文，叙述是讲清楚机制与动机）；不要复读代码（实现细节抄进文档必腐）；不要美化排版（结构清晰是全部）。

## 自查（五查，交 review 前逐条过）

| 查什么 | 判据 | 怎么查 |
|---|---|---|
| 1 查出处 | 每条规则能否回指素材 | 逐条对照素材原文（有校验工具可代查，无工具自查）|
| 2 查可判定 | 每条规则能否回答「怎样算违反」 | 逐条自问自答，violation 非空且不复读正文 |
| 3 查打架 | 条款间矛盾：数值冲突、行为定义冲突 | **本 skill 显式执行** |
| 4 查漏 | 状态机每个状态的事件都有去向；边界值穷举（空输入、极大值、并发、超时、临界点归属） | **本 skill 显式执行** |
| 5 查名实 | 同一概念多个名字（「用户/会员/账户」混用） | **本 skill 显式执行** |

五查必须在交付前逐条执行并在自查报告中留痕（发现什么、改了什么）——跳过即漏检。自查有效性的唯一裁判是漏检率：放行的条款后来被测试或人发现问题的比例，超标就收紧。

## 版本管控

- 版本号定稿才打，草稿期不打；所有引用以版本号为准；
- 每版变更记录只记差异：改了哪条（编号）、从什么改成什么、为什么、谁批；
- 条款编号稳定：小改编号不变；作废留痕（「R12 已作废，由 R15 替代」），不悄悄删除；
- 文档版本 ↔ 代码提交 ↔ 测试基线互相引用；能回滚并知道牵连范围。

## 配套对接（可选）

本 skill 独立通用，不绑定任何平台。若使用环境配有需求管理平台/CLI 工具（文档化交付、批注评审、版本基线），对接协议由该环境单独提供（接口文档或 CLI 说明），遵循其调用约定即可；无平台时产出物就是文档本身。
