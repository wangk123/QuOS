# 需求整理（req-organize）

把分散的意图收敛成一份可判定的共识文档，并维持其在时间轴上的有效性。

**文档是讲给读者听的故事：谁、在什么场景下、要完成什么、系统怎么帮他把事办成、办不成怎么办。** 行为约束是故事的一部分，以自然语言与结构块（表/图/状态链/异常）融在故事里，**不与故事并列成编号清单**——只有规则列表没有故事的文档是功能点堆砌，不合格；只有故事没有可判定约束的文档同样不合格。

## 角色分工

**AI 加工，人裁决。** 提取、聚合、自查、差异分析是 AI 的活；意图供给、共识确认、冲突终裁只能是人的活。AI 只能问，不能替用户想。

## 流程

1. **素材采集**：接受口述（快但失真）、碎片文档（断章）、代码（精确但会把实现偏差固化成需求——从代码反推必须标注送人确认）、记忆（重述走样）四类素材；
2. **提取聚合**：产出草案 + 问题清单。草案中 AI 推测补充的内容显式标注。问题清单只出三种题：选择题（给方案与后果）、确认题（写自己的理解让用户纠正）、填空题（问未定义的行为），不出阅读理解题；清单条目用**位置引用**（章节/场景/表行，不依赖条款编号），默认随草案附于文档末尾（定稿时移除）；正文内的批注标记由 review 阶段添加（见「与评审的关系」）；
3. **消歧循环**：提问 → 回答 → 再收敛，循环至问题清单清空；
4. **review 门（强制）**：草案必须经 req-review 检查，不通过按打回清单修改后重审，循环至全过。**修复轮的职责边界**：AI 只修打回清单上的文档病项，且只改清单指到的地方；标记项与问题清单项（歧义/缺失/不确定/待决）**一律停等用户裁决——不自答、不代删、不绕过、不擅自定方向**；连续挂起项随稿交付时集中列出送人。人的活 AI 做对了也是越权，做错了是事故；**每轮修复同步更新变更记录与过程记录**——旧轮次已失效的过程性声明（如「评审未执行」）必须同步作废改写，禁止文内自相矛盾；
5. **定稿与版本化**：用户逐项确认后定稿打版本号。

迭代（新素材 + 旧基线）同管线，多一步差异分析：新素材与基线的每个冲突强制用户二选一——意图演进（改文档）或实现偏差（改代码），不允许「先不管」。

## 文档骨架（从外到内，缺层即缺内容）

1. **文档头**：版本、日期、范围（**文档写不写**的覆盖面）、**读者对象**（这份文档写给谁看：用户方/开发/测试）。系统做不做归第 2 层管，两层不重复；
2. **背景与目标**：解决什么业务痛点（写痛点和价值，不是「系统是什么」的复述）；成功标准（可度量或可判定——素材缺量化指标时，从素材行为原则改写出**可判定的底线标准**并标注【AI 推测】送裁，不整体推给 TBD 空转）；明确不做什么及原因。问题不成立，后面所有功能都是无本之木；
3. **用户与场景**：用户类清单（谁、特征、使用频率、能干什么）；**直接操作系统的每个用户类至少一条端到端场景**（纯下游消费方可免）——角色 + 触发 + 与系统的交互步骤 + 结果 + 异常分支，用叙事体写成一个完整故事，且**写穿交互层**：每一步用户在哪个页面、看到什么信息、做什么操作、得到什么反馈，不允许写到「系统边界」就断；
4. **系统总览**：一段话说清系统是什么；主链路图；**上下文图**（系统边界：外部有哪些人/系统/依赖，数据往哪个方向流）；有用户交互面的系统给**页面地图与操作入口**（哪些页面承载哪些功能、关键入口在哪）——总览级导航，不是功能域章；
5. **功能域章（中段弹性，功能域即章）**：功能域 = 用户方能说出口的一摊功能事（受理、解析、分类、交付……），域的数量由需求内容决定，不设数字阈值。**文档存在多于一个功能域 → 每个功能域就是一个顶层章**（接在系统总览之后）；单一功能面的小需求（如一次安全增强）一章讲完，域作小节。**禁止「需求主体」「功能需求」类容器壳章**——把全部功能模块堆进一个大章，它是模板化石，与文档规模无关，任何规模下都没有存在理由（见下「章节组织」）；
6. **非功能需求**：性能 / 安全 / 可靠性 / 可维护性 / 合规，可判定，按实际需要取用，不凑满清单；
7. **约束、假设与开放问题**：外部依赖清单（挂了会怎样）、前提假设、待决问题（TBD 显式列出，不带进定稿）；
8. **术语表与变更记录**。

## 章节组织（需求主体怎么分章）

按**用户旅程/业务流程**或**用户可见的功能域**组织，功能域直接成章（不设「需求主体」容器层）；禁止把系统内部模块架构直接镜像成章节——内部实现怎么分层是设计文档的事。判据：拿目录问一个用户方读者，他能找到自己关心的那部分吗；10 秒找不到，就是域切错了或多了壳。

每章内部：**章首一段自然话**（服务哪个用户类的哪个场景、这章讲什么故事——一段讲完，禁止【为什么存在】【叙述】类标签拆段）→ 正文（图/表/状态链/异常块按内容取用）→ **行为约束融入叙述与块中**，不单独成规则列表节。页面与交互是各域用户可见行为的载体，在场景、总览与各域章中自然出现——**不是独立模块，也不是实现细节**。

## 写作纪律

- **功能必须挂到人**：每章必须能回答「服务哪个用户类的哪个场景」，答不出的降为实现细节、移附录或删；
- **背景写动机**：一两句事实性叙述，禁止出处引用句（「源自总览 2.3」是索引不是背景）；
- **约束融入叙述**：行为约束用自然语言写在故事里，或进结构块承载。测试点级断言、参数明细、字段列表、接口契约原文不进正文——它们是拆解产物或附属资料，倒灌进正文就是拿测试设计冒充需求；文档**不生成编号规则列表、不预铺「怎样算违反」**——可判定性是自查手段（见五查·查可判定），锚点与编号是评审/定稿阶段的派生物（见「与评审的关系」）；
- **交互是需求，不是实现细节**：页面、操作入口、操作流、系统反馈、错误提示、新用户上手路径，都是用户可见行为；禁止以「前端视觉规范」名义排除；交互复杂度（上手难度、操作负担）是背景与目标的合法考量。UI 级命名（页签/按钮字面）不强制逐项收录，但其承载的功能行为必须收；
- **结构化内容用块，不拆散**：参数表/清单 → `table` 块；主链路 → `figure` 块；状态跳转 → `states` 块；异常处理 → `exceptions` 块（含交互层异常：操作被拒/失败时用户看到什么、如何恢复）；叙述 → `para` 块。块是内容形态约定，与载体无关：无需求平台时 markdown 等价形态为——table=md 表格，figure=mermaid 图或「A → B → C」链路（可代码围栏），states=状态链或状态表，exceptions=编号条目列表，para=正文段落。同一批参数进了表就不再在正文复写（两处维护必漂移）；
- **主链路必须落图**：核心流程至少一条链路图，读者三十秒看懂主干。图只允许两种形态：mermaid 代码块，或线性「A → B → C」箭头链路（可多行，行首 → 续链）；**禁止 ASCII 盒子图**（┌─┐│▼ 画的框线图——需求平台无法结构化，只会整块降级成源码文本）；mermaid 节点文本里禁用半角括号 `()`（会被解析为形状语法导致渲染失败，用全角或·分隔），**节点 id 禁用 mermaid 保留字**（`graph`、`flowchart`、`subgraph`、`end`、`style`、`class`、`click` 等——撞保留字整图解析失败）；
- **数据实体可述**：核心业务实体（如订单/受理单/Run）及相互关系能从文档读出，实体多时给一条关系图；
- **术语表与正文一致（含专有名词）**：词条是正文实际在用的词，同一概念全文一个名字。素材自身同概念混用（如「子文件/子文档」）时：统一为一个名并在术语表登记别名；改名涉及业务叫法的，出确认题送用户。**系统名、接口路径、错误码、常量、枚举值、字段名是专有名词**——与素材逐字一致，中文叙述句中原样嵌入，不翻译不改写；素材未给出定义的词条，定义列标注【AI 推测】或出题送裁，不静默补写；

**三不要**：不要愿景渲染（叙述≠营销文）；不要复读代码（实现细节必腐）；不要凑模板（内容决定结构——章内要素图/表/状态链/异常按内容取用，无该要素的章省略不补，评审对章级要素缺失不机械打回）。

## markdown 格式契约（平台可渲染子集）

产出文档会进需求管理平台转换渲染，markdown 只用以下子集，超集会降级或丢失：

- **章节**：`## N 标题`（编号可带点），`### N.M` 自动挂子章，`#### ` 挂最近章；文档名用唯一 `# `；
- **表格**：标准 md 表格（含表头分隔行）；标题含「术语」的章节内表格自动成为术语表；
- **图**：仅两种——mermaid 代码块，或 ```text 线性「A → B → C」（可多行：行首 → 续链、├─/└─ 分支）；
- **图之禁忌**：mermaid 节点文本禁半角括号 `()`（形状语法冲突致整图渲染失败）；节点 id 禁保留字（graph/flowchart/subgraph/end/style/class/click，撞保留字整图解析失败）；禁 ASCII 盒子图（┌─┐│ 框线图网页必错位）；
- **列表**：每条独立一行（`-` 或 `1.`）；不用嵌套列表表达层级——用子章；
- **不使用**：`>` 引用块承载内容（导入时被丢弃）、行内 HTML、粗体强调（会被转为【】，直接写【】更好）；
- **生成侧不写锚点结构**：编号规则行（`- FR-101 …`）与【TBD-xx】双落点标注不在生成时预铺——批注标记与锚点由 review 阶段在正文添加（见「与评审的关系」），待确认问题以文末问题清单承载。但**内容可信度标注是内容本身的一部分，必须写**：凡素材未直接支持、由 AI 归纳推测的定义、数值、行为语义（含术语表的定义列），就地标注【AI 推测】或出题送裁——推测标注与 review 批注标记是两回事：批注是评审行为，推测标注是内容的诚实性，两者并存。

## 与评审的关系

本文档的产物是**干净、自洽、面向读者**的文档，不为评审或平台预铺机器结构：

- req-review 读这份干净文档。发现**歧义**（表述可多解）、**缺失不完整**（场景断链、异常无去向、交互层缺失）、**不确定**（无素材依据的推测）三类问题时，在**正文对应位置加轻量标记**——粒度任意：一段话、表格某个字段、一张图、一条状态链、一整个章节均可；
- md 交付时标记用 HTML 注释式（如 `<!-- q: 歧义|"领先差"是否含等号 -->`）：不占正文版面、不改变文档结构与阅读流；对接平台时由平台识别标记渲染为批注锚点；
- **标记是评审行为，不反向塑造文档结构**——不能因为要评审就把正文重组成编号列表或预铺锚点；条款编号等引用结构在**定稿或被引用时**才派生（与「版本号定稿才打」同构），草稿期文档不携带；
- 出处意识保留在自查（五查·查出处），不产生「规则条目 + quote 字段」形态的中间结构。

## 素材预裁决与自查

**素材预裁决不算终裁**：素材自带的裁决原则（如「文档与代码不一致时以代码为准」）只是素材内部口径；进入正式文档的每处需求-实现冲突，仍须逐项送人裁决。从代码/混合素材反推需求时，能逐条区分来源的逐条标注「实现反推」，混合素材按域标注实现状态，已知冲突逐条出题送裁。

## 自查（五查，交 review 前逐条过）

| 查什么 | 判据 | 怎么查 |
|---|---|---|
| 1 查出处 | 每处行为约束能否回指素材 | 逐处对照素材原文（有校验工具可代查；无工具时人工逐处执行）|
| 2 查可判定 | 每处行为约束能默想出至少一种**可观察的违反情形**，且该情形不是对原文的复述 | 逐处自问自答即可，**不落任何文档字段或附录**——可判定性是自查手段，正文保持干净 |
| 3 查打架 | 行为约束间矛盾：数值冲突、行为定义冲突 | **本 skill 显式执行** |
| 4 查漏 | 状态机每个状态的事件都有去向；边界值穷举（空输入、极大值、并发、超时、临界点归属） | **本 skill 显式执行** |
| 5 查名实 | 同一概念多个名字；契约标识符（接口/错误码/常量/字段名）被翻译或改写也是名实漂移 | **本 skill 显式执行** |

五查必须在交付前逐条执行并在自查报告中留痕——每查至少记「查了什么、发现什么、改了什么」，无发现记「无发现」，跳过即漏检。**五查 → req-review 门 → 打回修改 → 对改动处重跑相关查 → 重审**，这是固定顺序。自查有效性的唯一裁判是漏检率：放行的约束后来被测试或人发现问题的比例，超标就收紧。

## 版本管控

- 版本号定稿才打，草稿期不打；草稿多轮迭代用「draft-vN」文件标识区分，不算版本号。所有引用以版本号为准；
- 每版变更记录只记差异：改了哪处（位置/引句）、从什么改成什么、为什么、谁批；
- **引用结构（条款编号/锚点）定稿或被引用时才派生**，草稿期文档不携带编号结构；一旦派生则保持稳定，作废留痕，不悄悄删除；
- 文档版本 ↔ 代码提交 ↔ 测试基线互相引用；能回滚并知道牵连范围。

## 配套对接（可选）

本 skill 独立通用，不绑定任何平台。若使用环境配有需求管理平台/CLI 工具（文档化交付、批注评审、版本基线），对接协议由该环境单独提供（接口文档或 CLI 说明），遵循其调用约定即可；无平台时产出物就是文档本身。规则条目、锚点等机器结构不在生成侧预铺，由评审标记与平台侧约定承载。

本仓库环境（QuOS）提供 CLI：提交/拉取平台数据优先用 `uv run --directory server python -m app.cli <cmd>`（仓库根执行；文件传参，422 拒收明细完整输出 stdout 供修复闭环）。命令用法与调用纪律见 `docs/quos-agent-api.md`「CLI 调用」，端点契约见 `docs/api.md`。
