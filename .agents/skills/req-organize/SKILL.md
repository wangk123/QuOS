# 需求整理（req-organize）

把分散的意图收敛成一份可判定的共识文档，并维持其在时间轴上的有效性。

**文档首先是给人读的，其次才是给机器拆的。** 交付物是一篇读者读完能明白「系统是什么、为什么这样、怎么运转」的文档；规则编号是骨架，不是文档的全部。读者只看到规则堆砌、看不出原始需求长什么样的交付物不合格。

## 角色分工

**AI 加工，人裁决。** 提取、聚合、自查、差异分析是 AI 的活；意图供给、共识确认、冲突终裁只能是人的活。AI 只能问，不能替用户想。

## 流程

1. **素材采集**：接受口述（快但失真）、碎片文档（断章）、代码（精确但会把实现偏差固化成需求——从代码反推必须标注送人确认）、记忆（重述走样）四类素材；
2. **提取聚合**：产出草案 + 问题清单。草案中 AI 推测补充的内容显式标注，不冒充确定内容。问题清单只出三种题：选择题（给方案与后果）、确认题（写自己的理解让用户纠正）、填空题（问未定义的行为），不出阅读理解题；
3. **消歧循环**：提问 → 回答 → 再收敛，循环至问题清单清空。问不到的歧义会固化成条款里的暗坑；
4. **review 门（强制）**：草案必须经 req-review 检查，不通过的按打回清单修改后重审，循环至全过。详见 req-review skill；
5. **定稿与版本化**：用户逐项确认后定稿打版本号。

迭代（新素材 + 旧基线）同管线，多一步差异分析：新素材与基线的每个冲突强制用户二选一——意图演进（改文档）或实现偏差（改代码），不允许「先不管」。

## 写作纪律（什么是合格的文档内容）

- **背景写动机**：每个功能为什么存在，一两句事实性叙述。禁止写成出处引用句（「源自总览 2.3」不是背景，是索引）；
- **规则收敛到行为级**：一条规则说一个行为约束。测试点级断言、参数明细、字段列表、接口契约原文**不进规则 text**——它们是拆解产物或附属资料，倒灌进规则就是拿测试设计冒充需求；
- **结构化内容用块，不拆散**：参数表/字段清单/接口契约 → `table` 块；主链路流程 → `figure` 块（每行一条「节点 → 节点」链路）；状态跳转 → `states` 块；失败/超时/依赖挂掉的处理 → `exceptions` 块；衔接性叙述 → `para` 块。凡是被拆散塞进规则文本的表格内容都算违规；
- **主链路必须落图**：每个核心流程至少一条 figure 链路，让读者三十秒看懂主干；
- **章节按功能自然边界组织**：内容多的域用子章（`parent`）分层，不是每章都要凑齐所有块——缺状态机的章不写 states，没有异常路径的章不写 exceptions，内容决定结构；
- **术语表与正文一致**：词条是正文实际在用的词；同一概念全文只用一个名字。

**三不要**：不要愿景渲染和形容词堆砌（叙述≠营销文，叙述是讲清楚机制与动机）；不要复读代码（实现细节抄进文档必腐）；不要美化排版（结构清晰是全部）。

## 自查（五查，交 review 前逐条过）

| 查什么 | 判据 | 谁兜底 |
|---|---|---|
| 1 查出处 | 每条规则能否回指素材 | 平台硬校验（quote 定位）|
| 2 查可判定 | 每条规则能否回答「怎样算违反」 | 平台硬校验（violation 非空）+ review |
| 3 查打架 | 条款间矛盾：数值冲突、行为定义冲突 | **本 skill 显式执行** |
| 4 查漏 | 状态机每个状态的事件都有去向；边界值穷举（空输入、极大值、并发、超时、临界点归属） | **本 skill 显式执行** |
| 5 查名实 | 同一概念多个名字（「用户/会员/账户」混用） | **本 skill 显式执行** |

平台校验只覆盖第 1、2 查。第 3-5 查没有平台兜底，跳过即漏检——必须在提交前逐条执行并在自查报告中留痕（发现什么、改了什么）。自查有效性的唯一裁判是漏检率：放行的条款后来被测试或人发现问题的比例，超标就收紧。

## 版本管控

- 版本号定稿才打，草稿期不打；所有引用以版本号为准；
- 每版变更记录只记差异：改了哪条（编号）、从什么改成什么、为什么、谁批；
- 条款编号稳定：小改编号不变；作废留痕（「R12 已作废，由 R15 替代」），不悄悄删除；
- 文档版本 ↔ 代码提交 ↔ 测试基线互相引用；能回滚并知道牵连范围。

## 平台对接（QuOS v2 接口协议）

加工成果一律经平台接口提交，平台不内置 LLM；接口契约如下（基址默认 `http://127.0.0.1:8000`，本地无鉴权）：

### 调用顺序（短事务：唤起 → 拉取 → 加工 → 提交 → 退出）

1. `GET /api/v1/projects/{pid}/materials` — 拉材料清单（含 parsed_text，出处核对与 quote 复制的唯一来源）；
2. `GET /api/v1/projects/{pid}/doc/baseline` — 拉当前基线（无定稿返回 `{"empty":true}`，冷启动；有则增量加工）；
3. 加工（按本 skill 全流程 + 写作纪律）产出 DocPayload：`{meta, overview, glossary, new_terms, chapters, rules}`。章节含 `id/title/pri/parent(可选,父章节id)/background/blocks/rule_nos`，blocks 是正文块有序列表，每块 `{type: para|states|table|figure|exceptions, text?, title?, columns?, rows?, flows?, items?}`；rules 每条含 `no/text/violation/quote/material_id/status/replaced_by`；
4. **本地预检**：按 req-review 的判据过一遍（含第 3-5 查与可读性检查），打回项修完再进下一步；
5. `POST /api/v1/projects/{pid}/doc/draft` — body 即 payload 本体（无包装层）。**quote 必须从材料 parsed_text 原文复制**（NFKC+空白折叠后子串匹配；图片类材料 parsed_text 为空可豁免）；
6. `POST /api/v1/projects/{pid}/questions` — 批量提交消歧批注，元素 `{kind, payload, anchor}`：kind 限 choice/confirm/fill/scan；anchor `{chapter_id, rule_no?, seg?}` 把批注锚到正文片段（「术语确认」归 confirm，payload.klabel 区分）；
7. `GET /api/v1/projects/{pid}/questions?status=answered` — 下次唤起时取已答批注，据答案更新草案重新提交（覆盖 reviewing 旧草案）；
8. 全部批注收敛后提示用户在平台上「定稿发版」（版本号/说明由人定，agent 无发版权）。

### 校验报告处理纪律

- `POST draft` 硬错误 → 422，响应体 `{"detail":{"hard_errors":[{code, rule_no, detail}]}}`：**必须修正后重交，禁止绕过**。`QUOTE_NOT_FOUND` 的 detail.nearest 是材料内最相近片段，对照修正 quote；`BLOCK_*`/`CHAPTER_PARENT_*` 是正文块结构与层级错误，按 detail 修正；
- 软警告 → 平台自动转批注（source=auto，带 anchor），不阻塞入库；`new_terms` 由本 skill 自查申报（发现新词是 AI 职责，平台不猜词）；
- 编号口径：active 复用基线同编号 = 修改路径放行；**复活已作废编号会被拒**；作废必须显式 `status:"voided"` + `replaced_by`；
- 断点续跑：进度以平台状态为准（draft/questions/baseline），agent 不自记进度。

### 其他端点

`GET /doc/draft`（读当前 reviewing 草案）、`GET /doc/versions`、`GET /doc/changes?version=`（变更记录）、`POST /doc/finalize`/`POST /doc/revert`（仅人在平台操作）。
