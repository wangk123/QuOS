# 需求整理（req-organize）

把分散在人脑和多类载体中的意图，收敛成一份可判定的共识文档，并维持其在时间轴上的有效性。

## 角色分工（恒定原则）

**AI 加工，人裁决。** 提取、聚合、自查、差异分析是 AI 的活；意图供给、共识确认、冲突终裁只能是人的活。管线中不存在「AI 写、人读」的单向流。

质量守恒条件：每减少一分人的参与，必须补上一分机器可执行的验证（来源追溯 / 交叉一致性 / 测试映射）。人的参与量本身不是质量来源，可验证性才是。

人的不可减集合只有三项：
1. **意图供给**——需求在用户脑中，AI 只能问，不能替用户想；
2. **终裁**——文档与代码冲突时判定「意图演进（改文档）还是实现偏差（改代码）」；
3. **抽查**——监控自动放行部分的质量，防止整个回路悄悄劣化。

## 冷启动流程（素材 → 文档）

### 第 1 步：素材采集

接受四类异质素材，注意各自缺陷：口述（快但失真率高）、碎片文档（有结构但断章）、代码（最精确但意图缺失，会把实现偏差固化成需求——从代码反推需求时必须标注并送人确认）、记忆（每次重述走样）。

### 第 2 步：AI 提取聚合，产出三样东西

1. **文档草案**：结构化条款，每条带来源出处与置信标记（确定转写 / AI 推测补充）。推测部分显式标注，不冒充确定内容；
2. **问题清单**：没把握的地方出成题，只出三种题型——选择题（给方案与后果让用户选）、确认题（AI 写出自己的理解让用户确认或纠正）、填空题（问未定义的行为）。禁止出阅读理解题；
3. **自查报告**：见下方「AI 自查」。

### 第 3 步：消歧循环

AI 提问 → 用户回答 → AI 再收敛，循环至问题清单清空。这是形成过程的心脏：文档质量不取决于初稿，取决于提问的锋利度——问不到的歧义会固化成条款里的暗坑。

### 第 4 步：定稿（人的闸门）

用户对最小决策单元逐项确认后签字定稿。定稿即基线化，打版本号。

### 第 5 步：版本化

见「版本管控」。

## 迭代流程（新素材 + 旧基线 → 新基线）

与冷启动同一条管线，仅多一个前置环节：

1. **变更触发**：新口述 / 新碎片 / 代码变更 / 线上问题，任一均可；
2. **AI 差异分析**：新素材 vs 现有基线——增量是什么、与哪些既有条款冲突；
3. **人类裁决**：每个冲突强制二选一——意图演进（改文档 + 版本化）或实现偏差（改代码）。不允许「先不管」——那是漂移的入口；
4. **三方对齐**：文档、代码、测试重新对齐，对齐完成才算变更结束（是变更完成定义的一部分，不是事后补文档的自觉行为）。

## AI 自查（五查）

1. **查打架**：条款间矛盾（规则数值冲突、行为定义冲突），机器比对可抓；
2. **查漏**：状态机每个状态的事件是否都定义了去向；边界值是否穷举（空输入、极大值、并发、超时、临界点归属）；
3. **查名实**：同一概念是否用了多个名字（「用户/会员/账户」混用）；
4. **查出处**：每条能否回指素材，指不到的标「AI 推测」送人审；
5. **查可判定**：每条能否回答「怎样算违反」，答不出的挑出来重写。

### 自查有效性验证（防止无效空转）

自查有效性只有一个裁判：**漏检率**——AI 放行的条款后来被测试/人发现问题的比例。

- **埋错验证**：定期往文档埋几个错（改数字、藏矛盾），跑自查看能否抓出。抓不出的检查项判定为无效动作，加强或删除；
- **漏检归因**：每个漏出去的问题归类到具体检查项（查打架没抓到 / 根本没这类检查），据此决定加强哪个。

### 置信度分层与动态调节

高置信条款自动放行，低置信升级给人。阈值由抽检错误率反馈调节：错误率超标收紧，稳定放宽。这是带反馈回路的控制系统，不是静态分工表。

## 版本管控

1. **版本号**：定稿才打号，草稿期不打。版本号是「这一版共识」的名字，所有引用以此为准；
2. **变更记录**：每版只记差异——改了哪条（编号）、从什么改成什么、为什么（意图演进 / 修错）、谁批。变更记录是文档自身的记忆；
3. **条款编号稳定**：内容小改编号不变；整个作废则留痕（「R12 已作废，由 R15 替代」），不悄悄删除。编号是变更记录、测试点、用例断言的公共锚点；
4. **三方挂钩**：文档版本 ↔ 代码提交 ↔ 测试基线互相引用（提交信息中写文档版本号）；
5. **回滚能力**：能退回上一版并知道牵连哪些条款、代码、测试——这是版本管控的验收标准。

## 文档格式规范

### 组织形式

**按功能分章节（人的阅读单位），编号只挂在规则上（机器与追溯的锚点）。** 编号是章节里长出来的锚点，不是文档骨架。禁止把文档写成 R1…Rn 的条款罗列库。

### 骨架六件套

1. **文档头**：版本号、日期、范围（这版管什么、不管什么）——契约生效要件；
2. **变更记录**：见版本管控；
3. **术语表**：每个名词一个定义，全文统一用词；
4. **全景段**：系统是什么、给谁用、**初衷（为什么做，事实性三五句）**、明确不做什么。范围外内容混入是文档膨胀的起点；
5. **模块章节**：章节对应系统自然边界；
6. **图**：状态机图（有状态的）、流程图（多分支核心流程）、上下游链路图（跨模块长链路）——文本化（mermaid 类），带图号，图文同责（改行为不改图与不改文字同罪）。

### 章节内六件套

1. **背景初衷**：本功能为什么存在，一两句事实；
2. **状态与边界**：状态机（状态/事件/跳转）、规则边界值（临界点归属必须显式）；
3. **规则带编号**：每条可判定规则挂稳定编号；
4. **异常路径**：失败、超时、依赖挂掉时怎么办——必答项，不是可选项；
5. **非功能要求**：性能、安全、兼容性单列，同样可判定（「95% 请求 500ms 内」而非「要快」）；
6. **优先级 / 版本归属**：本期必须 vs 挪下版，防止拿未来版本要求误测当前版本。

### 三不要

不要散文（愿景渲染、形容词堆砌）、不要复读代码（实现细节抄进文档必腐）、不要美化（排版不产生消费价值，结构清晰才是全部）。

### 格式验收

把文档扔进拆分管线（req-breakdown）：AI 解析混乱=缺编号/结构；拆解拆不动=缺可判定/边界；用例断言没出处=缺来源；理解跑偏=缺术语表/全景。卡哪补哪。

## 执行纪律

- 全程不假装没有歧义：没把握就出题，不硬写；
- 所有「AI 推测」必须可见，混入确定内容即违规；
- 任何与现有基线的冲突必须送裁决，不得静默取舍；
- 修正文档时同步更新变更记录，无变更记录的修改视为未发生。
