# 需求整理（req-organize）

把分散的意图收敛成一份可判定的共识文档，并维持其在时间轴上的有效性。

**文档是讲给读者听的故事：谁、在什么场景下、要完成什么、系统怎么帮他把事办成、办不成怎么办。** 规则是这个故事沉淀出的约束，不是故事的替代品。只有规则没有故事的文档就是功能点堆砌，不合格。

## 角色分工

**AI 加工，人裁决。** 提取、聚合、自查、差异分析是 AI 的活；意图供给、共识确认、冲突终裁只能是人的活。AI 只能问，不能替用户想。

## 流程

1. **素材采集**：接受口述（快但失真）、碎片文档（断章）、代码（精确但会把实现偏差固化成需求——从代码反推必须标注送人确认）、记忆（重述走样）四类素材；
2. **提取聚合**：产出草案 + 问题清单。草案中 AI 推测补充的内容显式标注。问题清单只出三种题：选择题（给方案与后果）、确认题（写自己的理解让用户纠正）、填空题（问未定义的行为），不出阅读理解题；清单默认随草案附于文档末尾（定稿时移除），对接平台时转为批注提交；
3. **消歧循环**：提问 → 回答 → 再收敛，循环至问题清单清空；
4. **review 门（强制）**：草案必须经 req-review 检查，不通过按打回清单修改后重审，循环至全过；
5. **定稿与版本化**：用户逐项确认后定稿打版本号。

迭代（新素材 + 旧基线）同管线，多一步差异分析：新素材与基线的每个冲突强制用户二选一——意图演进（改文档）或实现偏差（改代码），不允许「先不管」。

## 文档骨架（从外到内，缺层即缺内容）

1. **文档头**：版本、日期、范围（**文档写不写**的覆盖面）、**读者对象**（这份文档写给谁看：用户方/开发/测试）。系统做不做归第 2 层管，两层不重复；
2. **背景与目标**：解决什么业务痛点（写痛点和价值，不是「系统是什么」的复述）；成功标准（可度量或可判定）；明确不做什么及原因。问题不成立，后面所有功能都是无本之木；
3. **用户与场景**：用户类清单（谁、特征、使用频率、能干什么）；**直接操作系统的每个用户类至少一条端到端场景**（纯下游消费方可免）——角色 + 触发 + 与系统的交互步骤 + 结果 + 异常分支，用叙事体写成一个完整故事；
4. **系统总览**：一段话说清系统是什么；主链路图；**上下文图**（系统边界：外部有哪些人/系统/依赖，数据往哪个方向流）；
5. **需求主体**（见下「章节组织」）；
6. **非功能需求**：性能 / 安全 / 可靠性 / 可维护性 / 合规，可判定，按实际需要取用，不凑满清单；
7. **约束、假设与开放问题**：外部依赖清单（挂了会怎样）、前提假设、待决问题（TBD 显式列出，不带进定稿）；
8. **术语表与变更记录**。

## 章节组织（需求主体怎么分章）

按**用户旅程/业务流程**或**用户可见的功能域**组织，禁止把系统内部模块架构直接镜像成章节——内部实现怎么分层是设计文档的事。判据：拿目录问一个用户方读者，他能找到自己关心的那部分吗。

每章内部：为什么存在（服务哪个用户类的哪个场景）→ 叙述（这章讲的故事梗概）→ 图/表/状态链/参数 → 行为级规则 → 异常路径。

## 写作纪律

- **功能必须挂到人**：每章必须能回答「服务哪个用户类的哪个场景」，答不出的降为实现细节、移附录或删；
- **背景写动机**：一两句事实性叙述，禁止出处引用句（「源自总览 2.3」是索引不是背景）；
- **规则收敛到行为级**：一条规则说一个行为约束。测试点级断言、参数明细、字段列表、接口契约原文**不进规则 text**——它们是拆解产物或附属资料，倒灌进规则就是拿测试设计冒充需求；
- **结构化内容用块，不拆散**：参数表/清单 → `table` 块；主链路 → `figure` 块；状态跳转 → `states` 块；异常处理 → `exceptions` 块；叙述 → `para` 块。块是内容形态约定，与载体无关：无需求平台时 markdown 等价形态为——table=md 表格，figure=mermaid 图或「A → B → C」链路（可代码围栏），states=状态链或状态表，exceptions=编号条目列表，para=正文段落。同一批参数进了表就不再在规则 text 里复写（两处维护必漂移）；
- **主链路必须落图**：核心流程至少一条链路图，读者三十秒看懂主干；
- **数据实体可述**：核心业务实体（如订单/受理单/Run）及相互关系能从文档读出，实体多时给一条关系图；
- **术语表与正文一致**：词条是正文实际在用的词，同一概念全文一个名字。素材自身同概念混用（如「子文件/子文档」）时：统一为一个名并在术语表登记别名；改名涉及业务叫法的，出确认题送用户；

**三不要**：不要愿景渲染（叙述≠营销文）；不要复读代码（实现细节必腐）；不要凑模板（内容决定结构，没有状态机的章不写 states，没有合规约束的项目不硬造合规章）。

**素材预裁决不算终裁**：素材自带的裁决原则（如「文档与代码不一致时以代码为准」）只是素材内部口径；进入正式文档的每处需求-实现冲突，仍须逐项送人裁决。从代码/混合素材反推需求时，能逐条区分来源的逐条标注「实现反推」，混合素材按域标注实现状态，已知冲突逐条出题送裁。

## 自查（五查，交 review 前逐条过）

| 查什么 | 判据 | 怎么查 |
|---|---|---|
| 1 查出处 | 每条规则能否回指素材 | 逐条对照素材原文（有校验工具可代查；无工具时人工逐条执行）|
| 2 查可判定 | 每条规则能否写出至少一种**可观察的违反情形**，且该情形不是对条文的复述 | 逐条自问自答（配套平台时可落为 violation 字段：非空且不复读正文）|
| 3 查打架 | 条款间矛盾：数值冲突、行为定义冲突 | **本 skill 显式执行** |
| 4 查漏 | 状态机每个状态的事件都有去向；边界值穷举（空输入、极大值、并发、超时、临界点归属） | **本 skill 显式执行** |
| 5 查名实 | 同一概念多个名字 | **本 skill 显式执行** |

五查必须在交付前逐条执行并在自查报告中留痕——每查至少记「查了什么、发现什么、改了什么」，无发现记「无发现」，跳过即漏检。**五查 → req-review 门 → 打回修改 → 对改动条款重跑相关查 → 重审**，这是固定顺序。自查有效性的唯一裁判是漏检率：放行的条款后来被测试或人发现问题的比例，超标就收紧。

## 版本管控

- 版本号定稿才打，草稿期不打；草稿多轮迭代用「draft-vN」文件标识区分，不算版本号。所有引用以版本号为准；
- 每版变更记录只记差异：改了哪条（编号）、从什么改成什么、为什么、谁批；
- 条款编号稳定：小改编号不变；作废留痕，不悄悄删除；
- 文档版本 ↔ 代码提交 ↔ 测试基线互相引用；能回滚并知道牵连范围。

## 配套对接（可选）

本 skill 独立通用，不绑定任何平台。若使用环境配有需求管理平台/CLI 工具（文档化交付、批注评审、版本基线），对接协议由该环境单独提供（接口文档或 CLI 说明），遵循其调用约定即可；无平台时产出物就是文档本身。
