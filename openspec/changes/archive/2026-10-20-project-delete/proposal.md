# Proposal: 项目删除（归档模块退役）

## Why

项目生命周期现状只有创建 / 改名 / 描述 / 归档 / 恢复，没有删除。归档只是从默认列表隐藏，数据与文件一直留在库里和磁盘上，试错项目、演示项目、传错材料的项目只能永久堆着。单人使用的工作台不需要「隐藏但保留」这一层：要么留着，要么删掉。归档模块整体退役，用删除替代。

## What Changes

已拍板 2026-10-20。

- **归档模块退役**：删 `POST /projects/{pid}/archive`、`POST /projects/{pid}/restore` 端点；`GET /projects` 去掉 `archived` query，始终返回全部项目；响应去掉 `archived` 字段；`Project.archived` 列从模型移除，启动时幂等 `DROP COLUMN`（存量库零手工迁移）；前端去掉「进行中 / 归档」切换、归档按钮、输名归档弹窗、恢复按钮。
- **新端点** `DELETE /api/v1/projects/{pid}`：物理删除项目及其全部从属数据（材料、草案、版本、基线、变更记录、批注、规则、术语）与磁盘上的项目目录 `data/<pid>/`。无前置条件。
- **前端**：项目总览每行加「删除」按钮，点击弹窗二次确认（显示项目名 + 不可逆警告），确认即删。
- **存量影响**：现库 id 1、2 两个项目处于归档态，退役后回到列表，可用删除清掉。
- **CLI 不动**：归档 / 恢复本就不在 CLI；删除是人侧闸门操作且不可逆，不进 agent 通道。
- **文档同步**：`docs/api.md` projects 节删归档两行与 `archived` 说明、加 DELETE 行；`docs/requirements.md` §4.1 生命周期句去归档加删除；spec `project-management` 删归档场景、加删除场景。

不做：软删除 / 回收站；输名确认（简化为普通二次确认弹窗）；删除前的「存在 reviewing 草案」拦截；导出备份后再删。
