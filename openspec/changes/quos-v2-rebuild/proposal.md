# Proposal: quos-v2-rebuild

## Why

v1(reqspec 模块)试用诊断出四个结构性问题:

1. **主产物错位**:「需求整理」产出 278 条规则条目库,粒度等于拆解层中间产物,人读不了;章节式画像(profile)是补救产物且大量空壳——整理被做成了拆解;
2. **标准焊死在代码**:格式标准、可判定标准硬编码于 `app/ai/tasks.py` 的 prompt 与 pydantic 模型,改标准即改代码;规则约束层不存在,平台四职责(工具汇总/规则约束/文档管理/交互体验)缺其三;
3. **AI 参与停留在单发调用**:7 个单发 LLM 任务无消歧闭环(未确认项堆挂不收敛)、无整文自查、质量无裁判(无漏检率度量)——AI 参与度与产出质量的双缺口同源;
4. **版本管理依赖 git 基线**:变更记录(差异+原因+批准人)、条款编号稳定、三方挂钩均缺失,profile 内局部重编号导致锚点失效。

结论:推倒重做(详见 `docs/adr/001`、`docs/adr/003`)。

## What Changes

- 新建 v2 平台:**统一标准接口**(材料读取/基线读取/草案提交/题目提交/答案读取)+ **两级校验闸门**(硬拒收、软转题)——平台成为 agent 产出的守门员;
- **存储换 SQLite 单库为唯一真相源**(原始材料文件留文件系统),版本自管(定稿快照+条款级变更记录),弃 git 基线与 MySQL 索引层(详见 `docs/adr/002`);
- **AI 加工外部化**:删除 v1 全部 LLM 编排;外部 agent 结合项目内 skill(`req-organize`)执行加工,平台只认接口提交的结果;
- **主产物换位**:章节式需求文档(按功能分章,给人读)为主产物,规则条目库降为锚点层(全局稳定编号、出处追溯);
- **人机闸门前端重做**:材料页、评审闸门页(四题型批量答题)、文档页(版本切换/变更 diff/定稿)、项目页;
- 旧数据不迁移;以「多模态」项目既有材料作为新链路验收用例。
