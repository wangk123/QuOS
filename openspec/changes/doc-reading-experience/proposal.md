# Proposal: doc-reading-experience — 需求文档内容质量与阅读体验(重构版)

> v2 重构(2026-10-15):按用户纠偏,主要矛盾从渲染样式改为**内容质量**——章节架构与章内编排;原渲染方案保留并降为配套阶段。实证来自多模态 draft 43(48 章/123 规则)与云风控对照。

## Why

平台已有的两份真实文档暴露了内容质量三类病灶(渲染再好也无意义):

1. **壳章堆叠**(多模态典型):md 骨架「## 需求主体」一级标题下塞入全部 10 个功能域,平台目录里 80% 内容挂在一个节点下。小需求(云风控,1 个功能面)一章收纳没问题;完整产品文档(多模态,10 域 123 规则)必须功能域顶层化。skill 骨架是固定八层,没有按规模伸缩的判据。
2. **章内骨架标签字面进正文**:每章以【为什么存在】【叙述】【规则】【异常路径】四个标签 para 硬开头——skill 的「章内顺序指引」被生成侧字面执行成标签,模板感即来源于此。
3. **结构化块形同虚设**:多模态全文 75 para / 11 table / 1 figure / 2 diagram / **0 states / 0 exceptions**;异常条目(「Profile 非 READY → 显式失败」句式)散落 para,状态链缺失。「要素按内容取用」纪律存在但无牙齿:生成侧不执行、导入侧不转换、评审侧不检查、平台侧不告警。

## What Changes

四个阶段,**A/B/C 是主体(内容质量),D 是配套(呈现)**:

- **A 章节架构弹性(生成侧)**:废除「需求主体」固定壳章层,骨架改为「头尾固定+中段弹性」;规模判据:功能域 ≥3 个或全文规则 >30 → 功能域直接顶层章;否则允许单章收纳。
- **B 章内编排去模板化(生成侧)**:章首「为什么存在+叙述」合并为一段自然开头(禁止字面标签);「先选形态后写文字」升级为硬纪律(异常必 exceptions、状态必 states、参数必 table);规则 >8 的章按子主题分组。
- **C 导入转换与平台校验(平台侧)**:md_import 三项归一——壳章提升(需求主体型壳章的子章上移顶层)、骨架标签剥离与开头两段合并、【异常路径】标签后条目转 exceptions 块;新增软告警三问(骨架标签残留 / 全 para 大章 / 壳章结构)转题进人闸门。
- **D 阅读呈现(前端,原 P0-P2 精简保留)**:章级主题色+速览+统计+滚动联动(零契约);行内 `**` 强调标记(保留+剥标记锚定+密度 lint);meta 可选字段(summary/keywords/reader_paths)与 cards 块、待确认汇总区。

## Impact

- **skills**:req-organize(骨架弹性、章内纪律、标记纪律)、req-review(新增章节架构组与章内形态组)。
- **平台**:md_import(三项归一)、validators(软告警)、models(可选字段)、DocPaper/style.css(渲染)。
- **兼容**:存量草案零迁移——重导经 C 归一后自然获得新结构;D 阶段全部可选字段缺省降级。
- **non-goals**:不做文档自动重组(架构由生成侧产出,平台只归一与告警);steps 步骤条块(与 figure/diagram 重叠);TBD 独立数据结构(走批注)。
